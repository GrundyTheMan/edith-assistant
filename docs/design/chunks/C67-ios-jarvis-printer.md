## Update 2026-11-20 (D39): the transport is C66a's, ordinary HTTPS
Everything below that says `PinnedHttp`, "C66's pinned transport", `requestBinary` or a hand-written HTTP client is **replaced by C66a's `JarvisApi` (over `secureFetch`)**: a long poll is an ordinary `fetch` that takes up to `wait` seconds (set the timeout to `wait + 10 s`), a camera frame is `res.body` read as bytes (`core/bytes.ts` `readBytes`) then Base64. Verify early that `expo/fetch` keeps a request open for 25 s on iOS. The package order, the strings, the safety model and the tests are unchanged.

## How this chunk relates to the Android design
C39 was written for Kotlin/Compose. **Its words, rules and screens are binding on iOS too** ("What the owner sees must behave the
same"): copy its **strings verbatim** (§6.2 the six page states, §7.5 the error words, §8.4 every card's text), keep its
**safety model** (§7 and the Jarvis spec §8: per-phone arming "Controls" that turns itself off, the server-enforced
confirmation, the cancel guard, emergency stop) and its **work-package order**. What changes is only the implementation
language and platform. Everything in this document is the translation table; **where this file is silent, C39 rules.**

## Rules that bite (from C39 §15–16; read them again before E7)
- **The server enforces confirmation** (`CONFIRM_REQUIRED` with the check) and Controls; the phone never decides a command is safe. Send `dryRun` first for commands C39 marks as needing the check, show the server's question, then resend with `confirmed: true`.
- **Nothing is ever tried on the real printer by an agent.** The owner decides what to try, one control at a time, printer idle first (C39 §13).
- Never send G-code or touch the printer except by the typed commands in the contract.
- The token and the camera frames are never logged; `FEED_ERROR` messages are generic.

## Tests

- [ ] **Owner, real Jarvis and printer (stage 1, then stage 2 one control at a time):** the page shows the real state, temperatures, files (after Load files), history, the camera; away from home over Tailscale too; stopping Jarvis shows the banner not a spinner; Controls turn themselves off; Pause/Resume on a real print; Cancel on a throwaway print; emergency stop last.

## Risks and unverified assumptions
- Long-poll through the hand-written HTTP client (C66 §2): a socket that stays open for `wait` seconds; verify the module keeps a connection idle for 25 s on iOS.
- Binary responses for camera frames through the same client; frame rate on a phone's CPU (Base64 in JS): measure; lower the rate before optimising.
- This is a large amount of UI: keep each card small, share a `Card` component, and resist inventing features beyond C39.

## Not in this chunk
Stages 3–4 (upload, start, delete, add-to-queue, alerts, recordings, live camera, screen taps).

## As built
Work packages land as separate PRs; each adds its own lines here. Nothing below has met a real Jarvis or printer (the Jarvis side of the connection is `jarvis-tailscale-listener-spec.md`, not built yet).

### E1 — Wire, commands, fixtures, pretend feed (built)
- `printer/feed/wire.ts`: the printer feed's data shapes (`PrinterState`, `StateAnswer`, `Check`, `SharedPrinter`, files, history, console, temperatures, macros), ported from Android's `PrinterFeedWire.kt` including the later Jarvis-review fields (`epoch`, `consoleSeq`, `features`, `schema`, `hidden` macros). **Every parser is total**: a missing field takes its default, a wrong-typed value is ignored, a state string from a newer Jarvis is shown rather than thrown on.
- `printer/feed/commands.ts`: all 33 commands as a typed union with `serializeCommand`, which writes the literal JSON Jarvis's validator reads (the kind first, fields in the declared order, unset optionals and an empty macro `params` left out). A table test lists every kind against its literal JSON and fails if a kind is missing. JavaScript writes `220.0` as `220`: the same JSON value.
- `printer/feed/fixtures/`: the 15 Android fixtures, copied unchanged. `printer/feed/testkit.ts`: **the pretend feed** for tests (not the Node script: that one serves a self-signed certificate, which Expo Go cannot use). It answers every route from the fixtures, records requests, can hold a long poll, and implements the Controls and confirmation behaviour; `connectedFeed()` gives a paired `JarvisService` talking to it. Test code only.

### E2 — The client (built)
- `printer/feed/api.ts`: `PrinterFeedApi` (one function per route over C66a's authenticated client; the `PrinterRoutes` interface is what the session and page take), the `CommandAnswer` mapping (`sent`, `checked`, `needsConfirm`, `refused`, `controlsOff`, `failed`) and `printer/feed/words.ts` (C39 §7.5's sentences, verbatim). Wait is capped at 25 s with a transport timeout of wait + 15 s; every value in a query is encoded; a dry run sends no request id; a retried send keeps its request id; a long poll is cancelled at once by its signal.
- Changes in C66a's client: failures now carry Jarvis's `code`, the HTTP `status` and the parsed `body` (a refused command's `check` is in it); an unreadable answer has the code `UNREADABLE`; `bytes()` answers camera pictures (3 MB cap, cancellable); `JarvisService.bytes()` and `sharedNow()`; `parseShared` carries the printer's share (`printerShare`).
- Tests: `wire.test.ts` (the Android assertions on the Android fixtures, plus "total" cases), `commands.test.ts`, `api.test.ts` (every route and every error mapping against the pretend feed). **Mutation-checked:** nine deliberate breaks (wait not capped, a request id on a dry run, a path glued into the URL, a confirmation not mapped, Controls-off not told apart, the kind not first, an empty `params` sent, a wrong field name, a default dropped) were each caught.

### E3 — The session (built)
- `printer/feed/feed.ts`: `PrinterFeed.access()` says what the app can do about the printer: **no Jarvis** (not paired), **not shared** (Jarvis shares no printer, or is too old to know it), **ready** (the client and what is shared) or **away** (Jarvis can't be asked; `removed` when it dropped this phone). It reads `/v1/shared` fresh each time (`JarvisService.readShared()`, new in this package).
- `printer/feed/session.ts`: `PrinterSession`, a port of Android's `PrinterSession`: `attach()` starts a loop that long-polls the `state` route (first question at once with no revision, then `after` + `epoch`, 20 s waits), `detach()` stops it and turns Controls off if the last answer had them on (best effort), `refreshNow()` asks again at once without a revision, `updatePresets()`. `state` is the page's state: `noJarvis`, `notShared`, `connecting`, `live` (with `offsetMs` = Jarvis's clock minus the phone's, and `stale` while the old page is shown after returning) or `away` (the last answer kept, with the reason). An unchanged revision publishes nothing; a new `epoch` (Jarvis restarted) is taken even with a lower revision. A failure waits 2, 4, 8 … 30 s and starts over after a good answer; an unreachable Jarvis re-reads what is shared when it returns; **a removed phone ("pair it again") and a stopped share end the loop, never retried**; a 429 waits 3 s with no banner. Every wait and the held poll are cancelled the moment the page leaves. The page's own timing (visible tab, `AppState`) is wired by E4.
- Tests: `session.test.ts` (19: the same cases as Android's `PrinterSessionTest`, over the pretend feed with waits the test ends by hand). The pretend feed now **holds the long poll by default**, as the real Jarvis does (an instant answer made the loop spin forever and crashed Node). **Mutation-checked:** ten deliberate breaks (backoff not growing, an unchanged revision published, the epoch ignored, leaving not stopping the loop, Controls left on, a removed phone retried (this one needed a stricter test), a stopped share looping, `quiet` never sent, the stale mark missing, an unpaired phone asking anyway) were each caught.

### E4 — The page skeleton and the Status card (built)
- `ui/printer/PrinterScreen.tsx` is a stack screen (`app/printer.tsx`) over Home. `PrinterPage` draws any state without the session (header with Back, name and connection chip; connecting spinner; full-page messages with Pair with Jarvis or Try again; a banner; collapsible cards); `PrinterScreen` attaches the session only while focused and Edith is in front, and detaches (and so turns Controls off) otherwise.
- `printer/feed/page.ts` holds the words for each state (chip, banner, message, alert), `format.ts` the number and time formats (the same cases as Android's PrinterFormatTest), `prefs.ts` which cards are folded (kept; Status, Camera and Temperatures open at first).
- `ui/printer/StatusCard.tsx`: title, state chip, progress, time left with its source note, elapsed, total, ETA, filament, layer, speed, flow, the job message, "Last print" (read once, only while idle) and the printer's alert with Dismiss.
- The Home printer tile has a Details button ("Printer page" until Jarvis is paired) that opens the page.
- Not verified: the page has not been seen against a real Jarvis (none exists yet); only the pretend one.

### E5 — The read-only cards (built)
- `printer/feed/cards.ts`: the pure rules ported from Android's `PrinterData.kt` (`ChartBuffer`, `ChartMath`, `FileList`, `ConsoleView`, `MeshColors`) and `PrinterCardData`, which reads what the cards need beyond the live state. It is lazy: the chart is seeded when Temperatures opens (and gets a point per live answer), history and console when they open, **the file list only when Load files is pressed**, the camera about every 700 ms only while its card is open (two failures in a row say "Camera offline"). Leaving the page stops all of it; a reply that arrives after leaving is dropped. New console lines are fetched only after the last one we have, when the live answer's `consoleSeq` is higher.
- `ui/printer/Cards.tsx`: Camera, Temperatures (chart drawn from plain Views: `react-native-svg` is not a dependency and Expo Go does not need it for this; at most 120 points per line; dashed means the target), Toolhead, Fans and light, Limits and retraction, Sensors, Filament slots (no slot is called empty when the printer does not report them), System, Queue and Bed mesh (left out when Jarvis sends none), Objects (bed drawing), History (totals, More), Console (read; "// value" lines hidden by default; Clear), Files (Load files, search, Printed before, details). Macros comes in E9; every control comes in E7–E9.
- Not built here: the chosen camera is not remembered across visits (Android remembers it); the file details are shown in the card, not in a sheet.
- Not verified: a real Jarvis (none exists yet), the look on the phone, the camera rate against the real 120-requests-a-minute limit.

### E6 — Home and chat fall back to Jarvis; settings text (built)
- `printer/feed/toHome.ts`: `deviceStateFromFeed` (Jarvis's `PrinterState` as a Home state, the same rules as Android's `PrinterToHome`: null when Jarvis cannot see the printer, Klipper not ready is an error with Jarvis's words, the printer's alert is the job's message when there is no other) and `FeedPrinterRead` (one `state` request with no wait, and only when the printer is shared).
- `PrinterService` takes an optional `jarvis` reader. It is asked **only** when the direct read says the printer is unreachable; never while the direct printer answers. Then the printer shows as online with `viaJarvis` (small "via Jarvis" on the tile) and no direct camera button. Any trouble (not paired, not shared, Jarvis away, an error) is "no answer": the tile stays "not reachable" as before.
- **Commands stay direct only**: away from home, Pause/Resume/Cancel on the tile say "Not reachable. It works on your home Wi-Fi. Open the Printer page to use it through Jarvis." and send nothing; they never ask Jarvis. (C39 §9.3: the tile's buttons never arm Controls.)
- `printer_status` says "(via Jarvis)" and adds "The printer's latest error line: …" while a print is going (not when the state already says it).
- Settings → Home → the printer's row has the paragraph (final words changed only in where to pair: "the Jarvis service above") and a status line: sharing the printer (name) / not sharing / not paired / can't be reached right now (`ui/PrinterJarvisNote.tsx`).
- Not verified: no real Jarvis; the tile's "via Jarvis" look on the phone. Stage 1 (read-only printer through Jarvis) is complete with this package, still unchecked against a real Jarvis.

### E7 — Controls and the confirm flow (built)
- `printer/feed/control.ts` (`PrinterControl`, ported from Android's `PrinterControl.kt`): the Controls switch (`setControls`, then the page follows Jarvis's own `arm` answer), `send` (a command goes out with `via: "phone"` and a new request id; a command the owner must confirm opens the sheet with **the server's** question and confirm words and sends nothing), `confirm` (sends again with `confirmed: true` and **the same request id**), `dismissSheet`, the 10-second self-closing sheet, the pending buttons, and the rules that end Controls: the page leaving or the app going to the background (`detached`, plus `session.detach` asking Jarvis to turn it off), a printer that is not ready, Jarvis away, and `CONTROLS_OFF`. A server that asks again after the owner's yes is not answered with another yes.
- `printer/feed/settle.ts`: a port of Jarvis's `commandSettled` and `settleTimeout` with its constants (all 33 kinds have a time; 0 means it does not wait). A button shows a spinner until the printer shows the change or the time is up.
- `ui/printer/ControlViews.tsx`: the Controls bar ("Controls on · 1:43", counted from Jarvis's clock; a look-only phone gets "Jarvis lets this phone look, not control."), the confirm sheet (Jarvis's words; red when dangerous; the other button says "Keep going", or "Keep printing" when the confirm says Cancel; never OK or Yes), **Emergency stop** in the header (works with Controls off and from a look-only phone, asks first, button "Stop now"), Pause/Resume and Cancel print on the Status card (reasons under them from the server's `quick` map), and a one-line message that goes after six seconds. The page has a coloured border while Controls are on.
- Not built here (E8–E10): the controls of the other cards, macros and the console input, and chat. The Files sheet's `onSent` hook exists for E8.
- Not verified: against a real Jarvis (the pretend feed has the contract's behaviour, not Jarvis's); nothing was tried on the real printer. **The owner decides what to try, one control at a time, printer idle first (C39 §13).**

### E8 — The controls of the cards (built)
- `printer/feed/input.ts`: what is typed into the boxes, ported from Android's `PrinterInput` (numbers with a comma or a dot, no hex; ranges with both ends; a target up to the heater's own maximum; extrude/retract 0.01-100 mm at 0.1-50 mm/s; limits and retraction send only the boxes that hold a number; the console line and the presets' rules, which E9 uses). An empty or wrong box leaves its button disabled; Jarvis checks every value again.
- `ui/printer/CardControls.tsx`: Temperatures (Set and Off for each heater, the presets from Jarvis, All off), Toolhead (Home all/XY/Z, a jog cross with the 0.1-100 mm steps, 100 mm is capped at 50 for Z, Z offset steps, Extrude and Retract, Motors off), Fans and light (sliders that send only when released, Light on/off, Internal/External/Stop air), Limits and retraction (speed and flow sliders, Apply limits, Apply retraction), the filament sensor's switch, Exclude an object (red; Jarvis asks), Queue (Remove, Start, Pause), System (Restart Klipper, Firmware restart, both red), the camera's "Turn camera on" when it says offline, and Print / Add to queue / Delete in a file's details. Each sends the literal command of E1; the server's refusal shows under the control that sent it ("Home the printer first." under a jog); a sent button shows busy until the printer shows the change; with Controls off or Jarvis away every control is disabled with the reason.
- A Files command Jarvis accepted closes the details, and a deleted file leaves the list without asking Jarvis for the list again (`PrinterCardData.commandSent`, hooked to `PrinterControl.onSent`). A stopped Klipper (shutdown or error) shows **Firmware restart** in the banner for a controlling phone.
- **Not built here:** editing the temperature presets and hiding macros need Jarvis's `settings` route, which the client does not have yet (E9 adds it with the macros); the file **upload** is stage 3.
- Not verified: against a real Jarvis or the real printer. **The owner decides what to try, one control at a time, printer idle first (C39 §13).**
